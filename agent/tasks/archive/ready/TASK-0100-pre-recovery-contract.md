# TASK-0100 — Provider-agnostic implementation-worker fallback router

## Status
READY

## Milestone
Infra (tooling/agent-workflow track — not part of the Kaizen product M1–M7 sequence; task IDs `0100+` are reserved for `tools/agents/**` infrastructure so they never collide with the product task sequence `TASK-0002`–`TASK-0006` reserved in `agent/tasks/INDEX.md`)

## Worker profile
HIGH

## Goal
Generalize `tools/agents/run_code_task.py` from a single-harness (Ollama-only) implementation-worker dispatcher into a provider-agnostic router that can dispatch through either the existing Ollama harness or a new OpenCode harness (OpenRouter, Groq, Cloudflare Workers AI, Google Gemini), selects an ordered worker chain from a task's declared `SMALL`/`MEDIUM`/`HIGH` profile, and preserves — without weakening — every existing safety property: Allowed-path enforcement, wrapper-owned independent verification, and fallback restricted strictly to genuine provider/access failures.

**Why this is classified `HIGH` (Worker profile rationale):** this task touches core dispatch/safety logic in `run_code_task.py`, introduces a second harness with real security implications (credential handling, restricted permissions), and must not regress the existing, already-hard-won Ollama path (DEC-0001/DEC-0002) or the independent-verification safeguards. Reasoning quality matters more than speed here.

- `opencode.cmd` must be installed and reachable (confirm via `opencode.cmd --help` as part of implementation, not assumed).
- No live provider API keys are required to complete this task: the automated verification plan below is achievable entirely through unit tests of the new pure-logic functions (classification, redaction, profile loading, long-lived-command denylist, verification-domain scoping) plus structural checks (a rung with no configured credential is skipped, never crashes). An actual end-to-end dispatch through a real `opencode` provider is explicitly **out of scope for this task's own verification** — it happens later, as the Orchestrator's own follow-up smoke test, once this task passes review.
- The root Kaizen application currently has a genuine, independently-reproduced `npm run build` failure (a Vite/Vitest type-version conflict, confirmed through four different providers, unrelated to this task). This task exists in part to make sure that failure **cannot** block this task's own dispatch (AC-25–AC-31) — it is not this task's job to fix the underlying app defect.
- **Bootstrap note (DEC-0003 §12–13):** this task edits `run_code_task.py` itself, so its own first dispatch's post-worker verification step runs under the *old* (pre-edit) in-memory code — Python does not reload a module because the file changed on disk mid-process. That old code has no domain-scoping and may report this task's own first dispatch `BLOCKED` solely due to the known, unrelated app build failure. This is expected, is not evidence of a real implementation defect, and is resolved by AC-32–AC-37's `--recheck` mode, invoked by the Orchestrator as a fresh, later process. See DEC-0003 §13 for the exact Orchestrator procedure.
- **Bootstrap note 2 (DEC-0003 §14–15) — which worker implements this task:** the old wrapper predates worker profiles and the "HIGH never auto-falls-back to local" rule, so this task must **not** be dispatched using the currently-active `ZOO_WORKER_MODELS=gpt-oss:120b-cloud,gpt-oss:20b` session chain unchanged — before dispatch, it must be pinned to `gpt-oss:120b-cloud` alone (a user action; the Orchestrator cannot set it inline). If that genuinely fails on a provider/quota signal, a supervised, one-time manual OpenCode dispatch is the documented contingency (§15) — not something this task's own code needs to special-case, and not a pattern to repeat for any other task.
- **Rework cycle 1 note:** the prior dispatch left `tools/agents/validate_task.py` in a broken state (see Rework requirements below) that causes `./tools/agents/validate-task` and `./tools/agents/run-code-task` to both crash immediately, for any task, before doing anything else. This rework cycle's dispatch may itself hit that same crash on the Orchestrator's pre-dispatch validation step — that is expected, is exactly item 1 of the rework, and is not a new defect to investigate separately.

## Forbidden changes
- Anything outside `tools/agents/**`.
- Any change to `src/**`, `package.json`, or any other Kaizen application file — this task does not touch the product.
- Any change to `.claude/worker-settings.json`, `.claude/settings.json`, or anything under `.roo/**` — the existing Ollama/Claude-Code harness's permission files are untouched by this task.
- Weakening, bypassing, or adding an escape hatch around Allowed-path enforcement, the implementation-report schema check, or wrapper-owned independent verification for either harness.
- Making fallback trigger on anything other than a genuine provider/access failure or a missing credential (see DEC-0003 §4). A code/test/lint/typecheck/build failure, a malformed report, or an Allowed-path violation must stop the chain exactly as it does today — never advance to another provider.
- Writing, logging, or printing any literal API key/secret value anywhere (file, log, stdout/stderr, prompt text, generated permission config). Redaction must be applied before any disk write, not as an afterthought.
- Removing or narrowing the existing `LONG_LIVED_SCRIPT_NAMES`-class protection once added — it must apply to both harnesses' output identically.
- Adding a new Python third-party dependency for this tooling layer (the project currently has none for `tools/agents/**`); use only the Python standard library.
- Pausing mid-task to ask a conversational question. If genuinely blocked by an unresolved ambiguity (e.g. OpenCode's real config schema cannot support the required restriction at all), stop and report **BLOCKED** with the specifics — do not guess silently and do not wait for input.
