# Decision — DEC-0003 — Provider-agnostic implementation-worker fallback (multi-harness router)

## Status
Approved / in effect. 2026-09-07.

## Why this is recorded
The user has validated four new implementation-worker providers beyond the two-model Ollama chain DEC-0002 established, and directed a specific set of architectural requirements for how they combine. This record generalizes DEC-0001 (worker permission/verification harness) and DEC-0002 (primary + local-fallback policy) into a provider-agnostic policy, and is the durable basis for `TASK-0100`, which will implement it. Nothing in this record changes DEC-0001's or DEC-0002's Ollama-specific mechanics — it extends them.

## What happened
The user tested, with real Bash execution through the actual worker harness, four additional providers reachable through the `opencode.cmd` CLI (OpenCode), alongside the existing two Ollama-hosted models:

| # | Harness | Provider | Model | Required credential (name only) |
|---|---|---|---|---|
| 1 | ollama | Ollama Cloud | `gpt-oss:120b-cloud` | none (existing Ollama sign-in) |
| 2 | ollama | Ollama local | `gpt-oss:20b` | none (local) |
| 3 | opencode | OpenRouter | `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` | `OPENROUTER_API_KEY` |
| 4 | opencode | Groq | `groq/openai/gpt-oss-120b` | `GROQ_API_KEY` |
| 5 | opencode | Cloudflare Workers AI | `cloudflare-workers-ai/@cf/openai/gpt-oss-120b` | `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` |
| 6 | opencode | Google Gemini | `google/gemini-3.8-flash` (high-reasoning variant available) | exact env var name(s) TBD — to be confirmed against OpenCode's actual provider docs by the implementing worker (commonly `GEMINI_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY`; not asserted here as fact) |

Cerebras was tested but requires payment and is explicitly excluded from the automatic fallback chain by the user's own instruction. It may be revisited later, but that would need its own decision (new paid vendor = a human decision gate under `AGENTS.md`).

## Decision

### 1. Two worker harnesses, one dispatch contract
- **`ollama` harness** — today's exact mechanism (`ollama launch claude --model <model> --restricted --settings .claude/worker-settings.json --tools Bash,Edit,Read,Write,Glob,Grep --permission-mode acceptEdits --permission-prompts none -p <prompt>`). **Unchanged.** This is the literal "preserve existing Ollama worker support" requirement.
- **`opencode` harness** (new) — dispatches the worker via `opencode.cmd` in non-interactive, one-shot mode, selecting a provider/model pair (`--model <provider>/<model-id>`, plus a reasoning-effort flag for the Gemini high-reasoning variant), against a **generated, task-scoped, restricted permission config** analogous to `.claude/worker-settings.json` (see §3).
- Both harnesses report through the same contract back to `run_code_task.py`: an exit code, captured stdout/stderr (redacted before anything touches disk — see §5), and the same required `agent/reports/implementation/TASK-XXXX.md` schema. Everything downstream of a harness call — Allowed-path violation detection, implementation-report schema check, wrapper-owned independent verification, move to `review/` vs `blocked/` — is **already provider-agnostic in the current code** and needs no behavior change; only the dispatch step itself is abstracted per-harness.

### 2. Worker profiles: SMALL / MEDIUM / HIGH, each an ordered rung list
A **rung** is one `(harness, provider, model)` triple with a human label. Rungs are data, not code — held in a new `tools/agents/worker_profiles.json`, not hardcoded in `run_code_task.py`, so profiles can be retuned without touching implementation logic.

**SMALL** — local-first, per the user's explicit "local `gpt-oss:20b` should remain preferred for suitably small tasks":
1. `ollama` / `gpt-oss:20b` (local) — primary
2. `ollama` / `gpt-oss:120b-cloud` — fallback if local Ollama itself is unavailable
3. `opencode` / Groq `groq/openai/gpt-oss-120b`
4. `opencode` / Google `google/gemini-3.8-flash`

**MEDIUM** — cloud-first, provider-diverse, no automatic local rung:
1. `ollama` / `gpt-oss:120b-cloud` — primary
2. `opencode` / Groq `groq/openai/gpt-oss-120b`
3. `opencode` / Cloudflare `cloudflare-workers-ai/@cf/openai/gpt-oss-120b`
4. `opencode` / Google `google/gemini-3.8-flash`
5. `opencode` / OpenRouter `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free`

**HIGH** — maximum capability/reasoning first, cloud-only automatic chain:
1. `ollama` / `gpt-oss:120b-cloud` — primary
2. `opencode` / Google `google/gemini-3.8-flash`, **high-reasoning variant** — strongest reasoning option tried early, since quality is prioritized over usage cost for the hardest tasks
3. `opencode` / Groq `groq/openai/gpt-oss-120b`
4. `opencode` / Cloudflare `cloudflare-workers-ai/@cf/openai/gpt-oss-120b`
5. `opencode` / OpenRouter `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free` — tried last: it is the free-tier, most rate-limit-prone option

**Rationale for the ordering differences:** SMALL prioritizes the free/private/fast local model since a small, tightly-bounded task doesn't need maximum capability. MEDIUM and HIGH both lead with the proven `gpt-oss:120b-cloud` primary; HIGH then reaches for the strongest available reasoning option (Gemini high-reasoning) before the other same-capability-class rungs, while MEDIUM tries the other `120b`-class provider-diverse rungs (Groq, Cloudflare) before spending the rate-limited free OpenRouter tier or extra reasoning effort it may not need. **HIGH and MEDIUM never automatically cascade into local `gpt-oss:20b`** — this is deliberate. Per the user's own requirement, local `gpt-oss:20b` is for "suitably small tasks and emergency task splitting," not a blind last resort for a large task's full, unreduced scope (this is the same principle DEC-0002 §4 already established: never blindly resend a large/loosely-bounded task to the 20B model). If every rung in a HIGH/MEDIUM chain is exhausted by genuine provider/access failures, the wrapper stops (`BLOCKED — all configured providers exhausted for this profile`) and the Orchestrator applies the existing DEC-0002 judgment: wait for quota to recover, or split the remaining work into smaller atomic tasks classified SMALL (which do include local `gpt-oss:20b`), preserving already-correct work exactly as DEC-0002 §5 already specifies.

### 3. Task-declared profile, not a session-only environment variable
`agent/templates/TASK.md` gains a new required heading, **`## Worker profile`**, whose value must be exactly `SMALL`, `MEDIUM`, or `HIGH`. This is the task author's (Architect's or Orchestrator's) classification, using the same rubric DEC-0002 already established informally (Allowed-path count, acceptance-criteria/rework-list size, dependency count, verification breadth) — now made durable and reviewable inside the task contract itself, rather than living only in an ephemeral shell environment variable. This directly fixes the friction DEC-0002 flagged (the Orchestrator's Bash tool cannot set an env var inline before dispatch).

**Backward compatibility / precedence:** if the environment variable `ZOO_WORKER_MODELS` is explicitly set at dispatch time, it is honored exactly as today — a raw, manual, full-override model list, bypassing profile lookup entirely. This preserves the currently-active `gpt-oss:120b-cloud,gpt-oss:20b` session chain and every other existing operational habit around `ZOO_WORKER_MODELS` unchanged. Profile-based selection is the new default path used only when `ZOO_WORKER_MODELS` is unset. `TASK-0001` (already in flight, blocked on an unrelated environment issue, no `## Worker profile` heading) is unaffected by this change and must keep working exactly as it does today; before `TASK-0001` is next redispatched, the Orchestrator will add a `## Worker profile: SMALL` line to its contract as a compatibility touch-up (a heading addition only, not a rework cycle, not a scope change).

### 4. Generalized, provider-agnostic failure classification
Today's `is_provider_quota_failure()` (textual scan for `429`/`quota`/`rate limit`/`usage limit`/`too many requests`/`402`) is extended to a `classify_worker_failure()` that additionally recognizes: `401`/`403`/"unauthorized"/"forbidden"/"invalid api key"/"authentication" (credential/auth failures), 5xx-class provider errors qualified by context words ("internal server error", "bad gateway", "service unavailable", "temporarily unavailable") to avoid false-positives on an unrelated "500" appearing in unrelated output, and connection/timeout failures **from the harness-launch process itself** (never from the independent verification step, which is a separate, later phase the classifier never touches). A **missing required credential** for an `opencode` rung (its provider's API key env var is unset or empty) is detected as a pre-flight check, before any subprocess is even launched, and is treated as fallback-eligible but logged distinctly as `credential_missing` rather than `provider_failure`, so a future audit can tell "the provider said no" apart from "we never had a key configured for it."

**Every other failure mode is explicitly excluded from fallback**, exactly as today: a nonzero exit with no provider/access signal, a missing/malformed implementation report, an Allowed-path violation, or — separately and always, regardless of which rung ran — a failure of the wrapper's own independent verification (`typecheck`/`lint`/`test`/`build`/etc.). None of these advance to the next rung. This is the existing `if not quota_failure: break` gate in `run_code_task.py`, generalized to the new classifier but structurally unchanged: **a bad implementation, a failing test, or a lint/typecheck/build failure stops the chain and reports BLOCKED — it never triggers a provider switch.** This is the literal mechanism that satisfies "do not fallback merely because code/tests/lint/typecheck/build fails" and "do not use provider switching to hide a bad implementation."

**Known limitation, stated honestly rather than glossed over:** classification by scanning captured text is inherently imperfect — a worker session that itself encounters an unrelated third-party "429" while doing something legitimate inside its sandbox could in principle be misread as a provider/access failure of the *harness itself*. This limitation already existed under DEC-0001/DEC-0002 for the Ollama-only case and is not made worse by this change; a more precise fix (structured exit codes/signals from each harness rather than text scanning) is a reasonable future improvement, out of scope here.

### 5. Credential handling — never on disk, never in the model's own context beyond what it needs
- API keys are read **only** from the process environment at dispatch time (e.g. `OPENROUTER_API_KEY`, `GROQ_API_KEY`, `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, and whichever Google credential env var OpenCode's own docs specify) and passed to the `opencode.cmd` subprocess **only via its environment**, never interpolated into prompt text, task files, or the generated permission config.
- Before anything is written to disk — a `.agent-worker/logs/*.log` file, a `fail_report()` attempt entry, an implementation/failure report — a redaction pass replaces every occurrence of every currently-set secret-shaped environment variable's value (name matches `*_API_KEY`/`*_TOKEN`/`*_SECRET`, or is one of the explicit provider variable names above) with `<redacted:VARNAME>`. This applies uniformly to both harnesses' captured output, not just OpenCode's.
- A rung whose required credential is absent is skipped (see §4), never crashed on with a traceback that might otherwise carry partial environment state.
- No task file, report, log, or prompt may ever contain a literal key value; this is an acceptance criterion on `TASK-0100`, not just a design intention.

### 6. Restricted OpenCode permissions, generated per task
`.claude/worker-settings.json` cannot be reused for the `opencode` harness, and — importantly — a functionally equivalent file **cannot live under `.claude/**` or `.roo/**` or `agent/**` either**, because `run_code_task.py`'s own violation check hard-forbids the worker from touching any path under those prefixes regardless of a task's declared Allowed paths. The restricted OpenCode permission template therefore lives under `tools/agents/**` (e.g. `tools/agents/opencode-worker-settings.template.json`, exact filename/schema to be determined by what OpenCode's real config format actually supports), instantiated per dispatch into a generated file under `.agent-worker/` (already gitignored, already the home of per-run prompts and logs), and must express the narrowest permission set that still lets the worker run the task's required `npm` commands — mirroring, in whatever schema OpenCode natively uses, the same intent as `.claude/worker-settings.json`'s narrow `npm install/ci/run build/run test/run lint/run typecheck/run check/run format:check`-only allowlist. **This document does not assert OpenCode's exact config schema as verified fact** — `TASK-0100` requires the implementing worker to confirm it against the real, installed `opencode.cmd --help`/documentation and capture that evidence in its implementation report, rather than guessing. If OpenCode's actual permission model cannot achieve npm-command-scoped restriction as narrowly as the Ollama/Claude-Code harness does, that gap must be reported honestly as a known limitation rather than silently accepted as broader-than-intended access.

### 7. The verifier must never be able to run a long-lived command — structurally, not just by wording discipline
`TASK-0001` cycles 8–9 demonstrated, twice, that relying on task-contract wording alone to keep `npm run preview` (a server that never exits) out of the wrapper's independent re-verification is fragile — a negation sentence still contains the matchable phrase. This decision requires a **structural** fix in `independent_node_verification()`, independent of and in addition to careful wording: an explicit denylist of script names that must never be auto-executed regardless of how they were named in the task's verification-plan text or discovered in `package.json` — `dev`, `start`, `preview`, `watch`, `serve` (case-insensitive exact name match) — plus a secondary content-based check on the script's command value (substrings like `vite preview`, `vite dev`, `--watch`, `nodemon`) as defense in depth against an equivalent long-running command hiding under a different name. Any script matching either check is dropped from the verifier's selected-checks list before execution and recorded in the verification summary as **refused (long-lived command, never auto-run)** rather than attempted. This applies to `ollama`- and `opencode`-produced code identically, since the verifier is already provider-agnostic.

### 8. Structured failure-attempt records
`fail_report()`'s per-attempt entries gain a `classification` field (`provider_failure` | `credential_missing` | `implementation_failure` | `contract_violation` | `verification_failure`) and a `harness`/`provider` field, so the Orchestrator (or a future session resuming from `agent/STATE.md`) can mechanically apply "provider failures do not consume the task's rework-cycle budget" (DEC-0002 §3, generalized here to every provider) by reading the failure report, instead of re-deriving it from raw logs by hand each time, as every prior cycle of `TASK-0001` required.

### 9. Windows compatibility
The `opencode` harness dispatch follows the exact pattern already proven for the `ollama` harness on this machine: `subprocess.run([...], cwd=ROOT, text=True, encoding='utf-8', errors='replace', capture_output=True, env=env)` with an explicit argument list (never a shell string), so no new `cmd.exe`-quoting or POSIX-only assumptions are introduced. `opencode.cmd` is invoked by its literal Windows binary name, overridable via a new `OPENCODE_BIN` environment variable (mirroring the existing `OLLAMA_BIN`).

## Addendum (2026-09-07) — task-aware verification scoping and a config-driven model registry
Before `TASK-0100` was dispatched, the user independently reproduced a genuine, pre-existing `npm run build` failure in the root Kaizen application (a Vite/Vitest type-version conflict, unrelated to this router work) through four different `opencode` providers (OpenRouter Nemotron, Groq GPT-OSS 120B, Cloudflare GPT-OSS 120B, Gemini 3.8 Flash) — confirming it is a real, standing project-level defect, not a per-provider fluke. This exposed a real coupling bug in `independent_node_verification()`: it unconditionally probes the root `package.json`'s standard scripts whenever that file exists, regardless of what a task's own Allowed paths actually cover — so a purely-infrastructure task like `TASK-0100` (Allowed paths: `tools/agents/**` only) would be spuriously blocked by an unrelated, already-broken application build. §10 and §11 below amend the architecture to fix this before implementation begins.

### 10. Independent verification must be scoped to the task's actual domain, structurally
**The problem, precisely:** `independent_node_verification()` today has no notion of task scope — it always runs whatever standard/explicit `npm` scripts `package.json` exposes, for every task, whether or not that task's Allowed paths have anything to do with the application. This is a real defect independent of the multi-provider work, now proven by direct reproduction, and it must be fixed as part of this task rather than left to bite `TASK-0100` on its very first dispatch.

**The fix — classify by structure, never by prose:**
- A new `INFRA_PATH_PREFIXES` constant (initially `('tools/agents/',)`, extensible later without a redesign) defines what counts as pure agent-tooling infrastructure.
- Immediately before verification, classify the task's **declared `## Allowed paths` patterns** (a required, wrapper-validated, already-structural field of the task contract — not free text) into one of: **INFRA-ONLY** (every pattern lies entirely under an `INFRA_PATH_PREFIXES` entry), **APP-ONLY** (no pattern does), or **MIXED** (a genuine combination of both). A pattern that cannot be unambiguously placed in one bucket (e.g. a wildcard broader than the known infra prefix, such as a hypothetical `tools/**`) is treated as spanning both — i.e. folded into MIXED, never silently treated as infra-only.
- As a second, independent structural cross-check, the actual changed-file set the wrapper already computes from `git status` after dispatch (used today for Allowed-path violation detection) must be consistent with the declared classification — every changed file must fall under an infra prefix for an INFRA-ONLY classification to hold, otherwise (or if there are zero changed files to check at all, e.g. a no-op dispatch) the wrapper falls back to running both verification classes. **This is the fail-closed rule:** classification can only ever narrow what verification runs, and only in the one case that is structurally provable twice over (declared Allowed paths *and* actual diff both confirm infra-only); every other outcome — including any ambiguity — runs at least everything today's code already runs.
- Two verification classes exist: the **infra class** (new, owned entirely by this task: `python -m py_compile` over changed `.py` files under `tools/agents/**`, plus `python -m unittest discover tools/agents/tests`) and the **app class** (today's unchanged `independent_node_verification` behavior against the root `package.json`, still subject to the long-lived-command denylist from §7). INFRA-ONLY tasks run the infra class only and never touch `package.json`. APP-ONLY tasks run the app class only, byte-for-byte as today. MIXED tasks run both.
- **Why this cannot become a worker-exploitable "skip verification" switch:** the classification depends on exactly two inputs, neither of which the worker authors or controls at verification time — the task's Allowed paths (fixed by the Orchestrator/Architect before dispatch, part of the same contract already governing what the worker may touch at all) and the wrapper's own independently-computed git diff (computed the same way Allowed-path violations already are, after the worker's process has exited). There is no field in the worker's prompt, session, or implementation report that this decision reads. A worker cannot request, claim, or hint its way into a narrower verification scope than what its actual declared task and actual diff structurally justify.

### 11. Worker model/provider identifiers are configuration, not code
`tools/agents/worker_profiles.json`'s SMALL/MEDIUM/HIGH chains (§2) reference **named slots** (e.g. `opencode-openrouter-nemotron-550b-free`), not raw model-id strings. A new `tools/agents/worker_models.json` registry maps each slot name to its concrete `{harness, provider, model, credential_env, reasoning}` definition. When a provider retires or renames a free-tier model — an expected, ordinary occurrence for the free tiers this decision relies on — updating that one registry entry's `model` field is the entire fix: no edit to `worker_profiles.json`, no edit to any `.py` file, no redesign of the router. This directly satisfies the durability goal the user named and keeps the profile-chain *shape* (which rung, in which order, for which task size) decoupled from the *identity* of any single model.

## Addendum 2 (2026-09-07) — the bootstrap problem: TASK-0100 modifies the code that verifies it
Before dispatch, one more structural gap was identified: `TASK-0100` edits `tools/agents/run_code_task.py` itself — the same file whose already-running Python process is doing the dispatching. This section states the problem precisely and defines the fix. **Nothing here pretends a running process picks up an edited file mid-execution — it does not, and no mechanism below assumes otherwise.**

### 12. Why the first dispatch of TASK-0100 cannot verify its own new logic in-process
`./tools/agents/run-code-task TASK-0100` starts one Python process. At import time, that process loads `run_code_task.py` **as it exists on disk at that instant** — the current, pre-`TASK-0100` version, since the worker hasn't run yet. The process then: validates the task, snapshots git state (`before`), launches the worker as a **subprocess** and blocks on it. The worker subprocess is what actually edits `run_code_task.py`, `common.py`, `worker_profiles.json`, etc. on disk. When the worker subprocess exits and control returns to the wrapper, **the wrapper's own process is still running the exact function objects it imported at start-up** — Python does not re-read a module from disk because a file changed underneath it, and this decision does not attempt any reload trick to fake that it does. So the wrapper's own post-worker verification step (`independent_node_verification`, or whatever `main()` calls next) is **still the old, pre-`TASK-0100` code** for the remainder of that one process's life — it has no domain-scoping (§10) yet, and will unconditionally probe the root `package.json`, which is where the already-known, independently-reproduced Vite/Vitest `npm run build` failure lives. **The first dispatch of `TASK-0100` can therefore end up BLOCKED by that pre-existing, unrelated failure, through no fault of the worker's actual (correct) implementation.** This is a one-time bootstrap artifact specific to a task that modifies the wrapper's own verification code; it does not recur for any other task, including every task dispatched after `TASK-0100` ships (those always start a fresh process that imports the already-current code from the very first line).

Separately, and unaffected by any of this: `git_dirty_state()`, `worker_changed_paths()`, `task_allowed_paths()`, and `path_allowed()` — the functions that enforce Allowed-path/diff protection — are **not modified by `TASK-0100`** (see its Allowed paths / ACs; no acceptance criterion touches them). The first dispatch's Allowed-path and changed-path enforcement is therefore already correct, using the same code as every other task, and needs no special handling. **Only the verification step is affected by the bootstrap gap** — this decision's fix is scoped to that step alone, not a wholesale re-architecture of the dispatch flow.

### 13. The fix: an explicit, narrowly-gated, fresh-process recheck mode — never a bypass
`TASK-0100` must implement a second, explicit CLI mode on the same approved entry point — `./tools/agents/run-code-task TASK-0100 --recheck` (exact flag name is the implementer's call; it must be explicit and task-scoped, not a general environment toggle). Invoking it is, by construction, **a brand-new Python process**, which imports the now-fully-updated `run_code_task.py` from disk — this is the entire mechanism; nothing more exotic than "run the command again, later, as its own process" is needed or attempted.

**Recheck is gated, not a free bypass.** It only proceeds when *all* of the following are structurally true (checked by the recheck process itself, from durable evidence already on disk — never from a flag the worker set or a claim in its own report):
1. The task is currently sitting in `agent/tasks/blocked/{tid}.md` (recheck never touches `ready/`/`active/`; it never invokes a worker, model, or rung — it consumes no provider quota and is not an "attempt").
2. The most recent `agent/reports/qa/{tid}-WORKER_FAILURE.md` shows **no** Allowed-path violation and **no** implementation-report-schema problem recorded — only a wrapper-owned verification failure. (Under the *old* code specifically, verification can only ever fail on a `package.json`-driven app-gate script, since the old `independent_node_verification` has no other check to run — so for `TASK-0100`'s own first dispatch this condition is equivalent to "the sole recorded failure is an app-gate script failing," without recheck needing to specifically string-match the known Vite/Vitest defect.)
3. `agent/reports/implementation/{tid}.md` exists and its own `## Status` does not itself claim `BLOCKED` for a substantive reason — i.e. the worker itself believed its implementation was complete.

If any of these is false, recheck refuses to run and says so — that outcome is a genuine implementation/permissions/report problem and must go through the **normal** rework cycle, exactly as any other task's failure would. This is the mechanism that satisfies "a different failure ... must still fail normally" and "no generic skip-quality switch": recheck's gate is a structural fact-check against durable evidence, not a judgment call or an override anyone can invoke at will.

**What recheck actually (re-)does, all with the freshly-imported, current code:**
- Re-reads the task's `## Allowed paths` from its contract (plain text — unaffected by any process boundary) and re-confirms the current working tree's dirty/changed paths are still all within them (redundant with the already-correct legacy check, kept anyway as the explicit defense-in-depth layer this decision requires).
- Re-validates the implementation report schema.
- Runs the **current** (domain-scoped, per §10) independent verification. For `TASK-0100` specifically, its own declared Allowed paths (`tools/agents/**` only) classify as `INFRA_ONLY`, so this runs the infra class only (`py_compile` + `python -m unittest discover tools/agents/tests`) and **never touches `package.json`** — this is what actually exercises the new logic for the first time, and is exactly what proves `TASK-0100` is not blockable by the known, unrelated app build failure. Because the required infra unit-test suite (AC-23) already covers every new pure-logic function — including redaction and credential-missing classification — running it via recheck is also what re-validates credential hygiene and the other unit-testable acceptance criteria; ACs that are not mechanically testable (e.g. AC-8's captured `opencode.cmd --help` evidence) remain the independent Reviewer's job to check by reading the report, same as always.
- On a genuine pass: moves the task from `blocked/` to `review/` and regenerates evidence (`collect-evidence`) — the same terminal state any normally-successful dispatch reaches, so everything downstream (the independent Reviewer) proceeds identically.
- On a genuine fail (the *new* code's own checks — Allowed paths, report schema, or the infra test suite/`py_compile` — actually fail): this is a **real** implementation failure. Recheck does not soften, retry, or paper over it; the task stays `blocked/` (or is returned to `ready/` with rework requirements, per the normal loop) exactly as it would from any other failed verification.

**Retry-cycle accounting for this one specific bootstrap case:** because the structured `classification` field (§8, an acceptance criterion of `TASK-0100` itself) does not exist in the *old* code that produces the first dispatch's own failure report, the Orchestrator makes this one call manually — by direct inspection of `agent/reports/qa/TASK-0100-WORKER_FAILURE.md`, using recheck's own gating preconditions (2)–(3) above as the test. If they hold, the legacy BLOCKED outcome is recorded as a **bootstrap verification-process gap, not an implementation failure**, and does not consume a rework/retry cycle — the same "read the evidence, judge honestly, don't blindly count an infrastructure artifact as a code defect" precedent already used for `TASK-0001`'s provider-429 cycles before `DEC-0002` existed as a formal record. Every subsequent task (including any rework cycle of `TASK-0100` itself, and every task dispatched after it ships) gets the fully mechanical, structured version of this same judgment via the `classification` field — this manual step is specific to `TASK-0100`'s own first dispatch and does not recur.

**How the Orchestrator proceeds, end to end:**
1. Dispatch `TASK-0100` normally (`validate-task` → `run-code-task`, using the currently-active `ZOO_WORKER_MODELS` override per §3's bootstrap note).
2. If it reaches `agent/tasks/review/TASK-0100.md` directly, the bootstrap gap simply didn't manifest (e.g. the app's `build` script happened not to be probed, or was already fixed independently) — proceed straight to the Reviewer. Recheck is a contingency, not a mandatory extra step.
3. If it lands in `agent/tasks/blocked/TASK-0100.md`, inspect the failure report against gating preconditions (2)–(3) above.
   - If they hold: this is the bootstrap gap, not a real failure (see retry-cycle accounting above); run `./tools/agents/run-code-task TASK-0100 --recheck`. If recheck passes, the task is now in `review/` — proceed to the Reviewer exactly as normal. If recheck also fails, treat it as a genuine failure and open a real rework cycle.
   - If they do not hold (a real Allowed-path violation, a report-schema problem, or the worker's own report claiming a substantive BLOCKED): this is an ordinary implementation failure — open a normal rework cycle. Do not run recheck; its own gate would refuse anyway.

## Addendum 3 (2026-09-07) — bootstrapping which worker implements TASK-0100 itself
One more gap, symmetrical to Addendum 2's verification-side gap but on the *dispatch* side: the currently-active session chain (`ZOO_WORKER_MODELS=gpt-oss:120b-cloud,gpt-oss:20b`) runs entirely on the *old*, pre-`TASK-0100` wrapper, which has no concept of worker profiles and no rule against auto-falling-back to local `gpt-oss:20b`. If used unmodified, a `gpt-oss:120b-cloud` provider failure during `TASK-0100`'s own dispatch would let the old code silently drop to local `gpt-oss:20b` — for a task classified `HIGH`, which this very policy says must never auto-cascade to local. This section defines the one-time procedure that prevents that, without requiring any code to exist before it's needed.

### 14. Primary path: pin the model list, no code change needed
Before `TASK-0100` is dispatched, `ZOO_WORKER_MODELS` must be set to `gpt-oss:120b-cloud` **alone** — not the two-model chain currently active in the session. This alone, with zero changes to `run_code_task.py`, makes it structurally impossible for the old wrapper to reach local `gpt-oss:20b` for this dispatch, because it simply is not in the list. As with every prior mention of this mechanism (DEC-0002's "mechanical note", DEC-0003 §3), the Orchestrator's own Bash tool cannot set an environment variable inline — this is an action for the user to take in their own shell before approving/triggering dispatch.

### 15. Contingency path: a supervised, one-time manual OpenCode dispatch — only on a confirmed provider/quota failure, never a template for future tasks
If the pinned `gpt-oss:120b-cloud` attempt fails, the Orchestrator reads `.agent-worker/logs/TASK-0100-1-gpt-oss_120b-cloud.log` and `agent/reports/qa/TASK-0100-WORKER_FAILURE.md` and classifies the failure exactly as `is_provider_quota_failure()` already does today (429/quota/rate-limit/usage-limit/too-many-requests/402). **A real implementation/code/test/security failure is not covered by this path** — it stops normally, exactly like any other task's genuine failure, and does not trigger any further attempt.

Only a confirmed provider/quota failure qualifies, and it does not consume a rework/retry cycle (same accounting principle as everywhere else in this decision). Because the pre-`TASK-0100` wrapper has **no OpenCode dispatch capability at all** — building that capability is the task's own deliverable — the Orchestrator cannot execute this contingency itself: it has no code to safely do so, and its own Bash tool is hard-restricted to the three approved scripts and read-only Git, never a raw `opencode.cmd` invocation. This step is therefore **user-executed, Orchestrator-specified, and Orchestrator-verified** — the only place in this entire architecture where a human performs a dispatch instead of the wrapper, and it exists solely to install the provider-agnostic router itself:
- The model is chosen from the four validated OpenCode options in the exact priority order the `HIGH` profile already defines (§2): Google Gemini `gemini-3.8-flash` (high-reasoning) first, then Groq `openai/gpt-oss-120b`, then Cloudflare `@cf/openai/gpt-oss-120b`, then OpenRouter `nvidia/nemotron-3-ultra-550b-a55b:free` last.
- The dispatch is restricted to `tools/agents/**` only and to the Python-only verification commands `TASK-0100`'s own contract permits (`python -m py_compile`, `python -m unittest discover tools/agents/tests`) — this task never touches `package.json`, so no `npm` access is relevant to it at all. Whoever runs this applies a restricted tool/permission configuration equivalent in intent to `.claude/worker-settings.json` (narrow, task-scoped, no unrestricted machine or repository access) — the Orchestrator can specify this intent and these constraints in writing but cannot author the actual OpenCode config file itself, since (per §6) such a file cannot legally live under `agent/**`, and the Orchestrator cannot write outside `agent/**` at all.
- The dispatch target is `agent/tasks/ready/TASK-0100.md` (or `active/`, if the Orchestrator has already moved it there) as the contract, and `agent/reports/implementation/TASK-0100.md` (`agent/templates/IMPLEMENTATION_REPORT.md` schema) as the required report — identical to what the wrapper itself would require of any worker.
- **This procedure is not a general bypass and must not be reused.** It exists only because nothing can yet dispatch to OpenCode before `TASK-0100` ships. Every task dispatched after `TASK-0100` is implemented and reviewed — including any future task large enough to need OpenCode as a genuine fallback — goes through the fully automated, wrapper-owned harness this task builds. If this exact situation (a task modifying the router's own dispatch code, primary rung unavailable) ever recurs, it needs its own fresh decision record at that time, not a silent reuse of this one.

**Reconciling either path with `--recheck` (§13):** if the ordinary wrapper path (§14) itself lands the task in `agent/tasks/blocked/TASK-0100.md` with its own `WORKER_FAILURE.md`, `--recheck`'s existing gating preconditions apply directly, exactly as already specified — nothing new needed. If §15's manual path was used instead, the task never went through the wrapper's own move-to-`blocked/`/evidence-writing logic, so the Orchestrator performs the equivalent placement itself, entirely within its own `agent/**` write scope: it independently confirms (via its own permitted read-only `git status`/`git diff`, no elevated access) that the actual changed files lie entirely within `tools/agents/**`, then writes a `agent/reports/qa/TASK-0100-WORKER_FAILURE.md` recording the real, quoted provider/quota evidence from §14's failed attempt and noting a §15 manual dispatch is believed complete, and moves the task file to `agent/tasks/blocked/TASK-0100.md`. This is a factual record of what actually happened, populated only with real, verified evidence — never a fabricated or assumed pass. With that in place, `--recheck`'s preconditions (§13) apply identically regardless of which path produced the diff; `--recheck` itself needs no changes and does not need to know which path was used.

After a genuine pass — via `--recheck` or directly — proceed to the independent Reviewer exactly as §13 already documents.

## Alternatives considered
- **A single unified "just try every model in one flat list" chain**, ignoring task size. Rejected — this is exactly the "blindly resend a large task to the small model" failure mode DEC-0002 already identified and rejected for the Ollama-only case; a flat list can't express "local is preferred for small tasks but never auto-reached for large ones."
- **Route profile selection through an environment variable only** (`ZOO_WORKER_PROFILE`, mirroring `ZOO_WORKER_MODELS`). Rejected as the primary mechanism (kept as a manual override escape hatch is unnecessary complexity beyond what's asked, so not added at all in v1) in favor of a task-declared heading — durable, versioned, reviewable, and removes the exact operational friction DEC-0002 §"Mechanical note" already flagged about the Orchestrator's Bash tool being unable to set env vars inline.
- **Store OpenCode credentials in a committed or task-local file.** Rejected outright — explicit requirement violation ("never expose API keys in task files, reports, logs, prompts, or git"); environment-variable-only sourcing is the only option considered.
- **Let the verifier keep trusting task-contract wording alone to avoid long-lived commands.** Rejected — already empirically failed twice (`TASK-0001` cycles 8 and 9); a structural denylist is required in addition.
- **Auto-cascade HIGH/MEDIUM failures straight into local `gpt-oss:20b`** as a blind final rung. Rejected — violates the user's own framing of local as being for "suitably small tasks and emergency task splitting," and repeats the exact anti-pattern DEC-0002 §4 already rejected.

## Cost / payment impact
No new paid vendor is being added. Per the user's own validation: OpenRouter's `:free` model tier, Groq, Cloudflare Workers AI, and Google Gemini are all currently exercised on free tiers. Cerebras is excluded specifically because it requires payment — the user already applied the "new paid vendor needs a decision gate" rule themselves by excluding it rather than asking for approval to add it. If any of the four newly-added providers' terms change to require payment, or usage crosses into a paid tier, that is a new decision requiring its own gate at that time — noted here as a forward-looking flag, not a current blocker.

## Security / privacy / confidentiality impact
Net effect is containment, matching DEC-0001's original framing: credentials are sourced only from the environment, never written to a task file, report, log, or prompt (redaction pass enforced before any disk write), never interpolated into text a worker/model session could echo back, and a missing credential fails closed (rung skipped, not silently attempted with an empty key). The `opencode` harness's restricted-permission mechanism is required to be genuinely verified against OpenCode's real config schema rather than assumed, and any gap versus the Ollama harness's narrower guarantee must be reported honestly rather than hidden. No change to the Orchestrator's own `.claude/settings.json` permission boundary (still writes only `agent/**`, still cannot run arbitrary Bash) — this decision only extends the *worker's* dispatch mechanism, exactly as DEC-0001 did.

## Consequence of postponing
`TASK-0001` (and all subsequent M1 tasks) remain dependent on Ollama alone, with no resilience against `gpt-oss:120b-cloud`'s provider quota (already hit twice — cycles 6 and 7) beyond the single local `gpt-oss:20b` fallback. The four newly-validated providers stay unused capacity. Not urgent — `TASK-0001` can and does continue to function on the existing two-rung Ollama chain in the meantime — but the resilience and quality-of-fallback benefit is deferred until this ships.
